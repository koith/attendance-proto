# QA1243 신규 지점·점주 권한 최종 준비

기준 main: `3f3d5cdd8bb8640c6ac74480c429e0f17bf0c7f9` / 앱 v0.363.
이 변경의 배포 후보는 v0.364이며 실제 배포 성공 전 현재 운영 버전으로 보고하지 않는다.

## 이번에 닫은 기술적 빈틈

메일의 일회용 recovery 링크를 열면 토큰이 URL에서 바로 지워지지만, 기존 코드는 최종 권한 등록·새 비밀번호 로그인까지 끝나기 전 인증을 보관하지 않았다. 그래서 새로고침이나 초기 네트워크 오류 뒤에는 이미 사용된 링크를 다시 열 수 없어 진행이 막혔다. 수정 전 두 시나리오를 실제 클라이언트 VM으로 재현해 FAIL을 확인했다.

수정은 한 탭의 `sessionStorage`에 인증 토큰만 최대 1시간 보관한다. 비밀번호를 저장하지 않고 기존 본사/main 앱의 로그인도 덮어쓰지 않는다. 매 복구 때 실제 Auth 사용자와 서버 초대 preflight를 다시 확인하며, 계정·지점 변경/취소/만료는 거부하고 임시 상태를 지운다. 만료된 access token은 refresh token으로 한 번만 갱신하며, 회전된 토큰의 사용자도 일치해야 한다. 역할 확인과 새 비밀번호 실제 로그인 뒤에만 기존 main 앱 세션을 저장한다.

배포는 정확한 클라이언트 파일·버전 변경만 허용하는 기존 정적 Pages 경로를 사용한다. 운영 Sheets 갱신·실메일·Auth 설정 변경·권한 부여·READY·SEC01은 배포 작업에 포함하지 않는다. 배포 전후 다른 운영 자산의 해시와 새 index/HTML/JS의 공개 바이트를 비교한다.

- 대표 최초 로그인 재시도: PR1392 / main3f3d5cdd / 82개 workflow 성공, Pages40341823100 v0.363.
- 근무현황 복원·중복정정: PR1381/1383, v0.360, Pages40257068081. ADD108/109는 VOID_ADD124/125로 취소됐고 원본5590과 EDIT_TIME107은 보존됐다. 운영 DB에서도 같은 상태를 확인했으므로 재정리하지 않는다.
- 기존 격리 Auth/SMTP/JWT/PostgREST·보조 관리자·지점 격리 및 Google E2E 성공 기록은 소스/환경의 적용 범위 내에서 재사용한다. 실제 점주 인증 성공으로 대체하지 않는다.
- 새 클라이언트 회귀9 + 기존 재시도4 + 운영 무쓰기 배포 범위4 = 17개 PASS. 별도 기존 최초로그인 보안 계약·Pages/Google 무쓰기 guard도 PASS. 실제 개인 로그인 완료와 구분한다.

## 실제 지점80 개통 게이트

읽기 전용 조회 시 `REAL_1 / STAGED / is_active=false`, admin_users0, primary_owners0이다. 임시 대표 초대 기록만으로 대표 권한 부여/READY 성공이라고 보고하지 않는다.

1. 실제 수신자가 현재 유효한 메일/세션으로 본인 인증하고 개인 비밀번호를 확정한다.
2. 서버가 실제 현재 비밀번호·초대 유효기간·동일 사용자/지점을 확인해 대표를 등록한다.
3. 새 비밀번호의 실제 로그인과 해당 지점 권한을 확인한다.
4. 공식 개통 증빙·시연 데이터 제외·대표 확정 등 기존 READY 조건을 확인한 뒤 본사가 개통을 승인한다.
5. 해당 실운영 작업의 원본/타지점 데이터 불변을 전후 확인한다.

최신 실메일의 수신·링크 클릭·실세션 성공 증거가 없으므로 QA-04/AUTH-01/FIELD-01을 체크하지 않는다. 임의 비밀번호 설정/실초대 재발송/READY 전환으로 이 절차를 대신하지 않는다.

## 별도 보류·개통 이후 범위

- SEC-01은 기존 영향/복구·격리 검증을 재사용하되 운영 활성화·실기기 검증은 별도 승인 전 실행하지 않는다.
- PR1365의 설명은 지점80이 READY/대표확정이라고 가정하지만 현재 DB는 STAGED/대표0이다. 최신 Edge와 재대조 전 자동 Sheets 생성의 근거로 사용하거나 병합하지 않는다. 새 지점 Sheet 준비와 기존 인하대 Sheet 보존을 분리한다.
- PR1361의 GAS 메일 브리지는 여전히 실제403/미병합이며 대체 메일 경로의 미완료 개발이다. 실제 사용 중인 Native Auth 메일의 성공 여부와 혼동하지 않는다.
- POS/배달/공급사/장바구니/실판매량 연동은 미완료 후속 자동화다. 신규 지점의 별도 개통 필수조건으로 임의 추가하지 않는다.
