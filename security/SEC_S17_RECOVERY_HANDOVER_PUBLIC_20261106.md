## 3. 데이터 유실 방지 복구 순서 (실행 절차 아님)

1. **동결 전제 확인:** 복구하려는 운영 데이터의 소유·접근·승인 범위 확인. 기존 서비스 정상 운영을 유지하고, 원본 DB·백업·근태 정정 이력을 삭제하지 않는다.
2. **보관물·메타데이터 확인:** 각 암호화 백업의 생성 시점, 대상 버전·스키마, SHA-256, 객체 목록과 보유 범위 확인. 관리형 Auth 설정/권한·Storage 실파일·Edge/GAS 설정을 별도로 인벤토리화한다.
3. **일관성 증명:** 운영 DB를 임의 시점에 여러 번 SELECT하여 얻은 테이블 해시들을 단일 백업 스냅샷으로 오인하지 않는다. 복구 비교는 실제 해당 백업 스냅샷에서 확보된 동일 시점 자료로 수행해야 한다.
4. **격리 복원:** 사용자 업무와 단절된 임시 PostgreSQL/서비스에 역할→스키마→데이터→제약·시퀀스·RLS·정책→Auth·Storage를 적용. 개인키는 오프라인 접근 통제, 임시 평문은 제한 권한·확실한 삭제; 운영 환경에 직접 복원하지 않는다.
5. **손실 없는 델타 재적용 연습:** 백업 이후 새로 추가·취소·정정된 근태/급여 이벤트를 분리된 불변 원장으로 보관한 뒤, 일관된 기준 시점·ID·순서·원본 참조·중복·충돌을 검증한다. 기존 운영 데이터를 덮어쓰는 `pg_restore --clean` 사용을 금지한다. 합성 `reapply_guard`는 안전성 탐색용일 뿐 운영 DB 트랜잭션을 대신하지 않는다.
6. **독립 증거:** DB 대상 행수와 데이터/DDL/객체 바이트·해시 비교, Auth 실제 로그인/구세션 차단, Storage HTTP/RLS, Edge 권한별 401/403, GAS/Sheets 격리 쓰기·재조회, 모바일/PC 회귀를 각각 PASS/FAIL/UNVERIFIED로 분리한다.
7. **안전한 중단·롤백:** 항목 중 하나라도 미검증이면 운영 전환 NO_GO. 실제 사용자 근태/급여 변경은 보존하고, DB 전체 시점 복구 대신 코드/설정 롤백과 증분 재적용 등 검증된 대안을 사용한다.

## 4. 운영 복구 승인 전 필수 체크리스트

- [ ] 실제 봉인된 **전체** DB/Auth/Storage 백업 원본·제조 시각·상호 일관성·SHA-256 및 별도 보관 장소 증명
- [ ] 백업 해제키의 **별도 보관**, 분실/교체 복구, 접근·회수 승인 (키 내용 공개 보고서에 기록 금지)
- [ ] 격리 PostgreSQL에 완전 DDL/역할/정책 및 데이터 복원 성공, 소스 백업 스냅샷과 비교
- [ ] GoTrue/Auth 실제 격리 로그인·세션 폐기·SMTP/링크 설정 및 서비스별 보안 확인
- [ ] Storage 파일 바이트/메타데이터/RLS 및 API 제공 결과 독립 확인
- [ ] 백업 이후 근태·급여/정정 이력 **무손실** 재적용, 중복/재시도, 테스트 금액 일치
- [ ] Edge/Pages/GAS/Sheets 버전 호환·비인가 접근·격리 보고서 쓰기 검증
- [ ] 실제 PC·iPhone 관리자/직원 정상 업무 수용
- [ ] RPO/RTO **실제 측정** 및 복구 실패·반송·재시도 절차, 이력/승인 기록
- [ ] 운영 키·소유권·권한 **인수인계 승인**, 최소권한 부여와 회수 증거

**RPO와 RTO는 현재 `UNVERIFIED`**. 코드 및 자동화 테스트가 빠르다고 임의의 복구시간·유실허용시간을 적지 않는다.
